# ADR-001: 클라우드 백업 백엔드 플랫폼으로 Supabase 채택

- 상태: **Proposed** (TBD-013 확인 후 Accepted)
- 날짜: 2026-10-30
- 관련 결정: D-010, D-011, D-012, D-015, D-016, D-019
- 관련 요구사항: FR-CLOUD-01~10, NFR-01, NFR-03, NFR-05

## 배경

D-010으로 백엔드를 도입하고, D-011로 범위를 "로컬 우선 + 로그인 사용자 선택형 클라우드 백업"으로 정했다.
필수 조건은 다섯 가지다.

1. 카카오 로그인 + 이메일 매직링크 (D-012)
2. 사용자별 백업 데이터 저장
3. 사진 축소본 파일 저장 (D-015)
4. 서버 측 계정 격리 (NFR-01)
5. 계정 삭제 시 전체 삭제 (D-016)

1인 개발이므로 직접 작성하는 보안 코드의 양과 운영 부담도 기준이다.

## 결정

Supabase(Postgres, Auth, Storage)를 사용한다.

- 계정 격리는 Postgres 행 수준 보안(RLS)으로 DB가 강제한다.
- 로그인·백업 SDK(`@supabase/supabase-js`)는 **지연 로딩**한다. 게스트의 첫 화면에는 포함하지 않는다.

## 근거

| 기준 | Supabase | Firebase | Vercel 조합(Postgres + Blob + Auth.js) | 직접 서버 |
|---|---|---|---|---|
| 카카오 로그인 | 기본 지원(미확인) | 기본 미지원(미확인), 토큰 교환 함수 직접 작성 | Auth.js 제공자(미확인), Vite 연결 코드 필요 | 직접 구현 |
| 매직링크 | 기본 | 기본 | 직접 조립 | 직접 구현 |
| 서버 측 계정 격리 | RLS(DB 강제) | 보안 규칙 | 앱 코드 | 앱 코드 |
| SDK 크기(gzip, 실측) | +58.2KB | +170.1KB | — | — |
| 운영 부담 | 낮음 | 낮음 | 중간 | 높음 |

**SDK 크기 측정 조건 (2026-10-30):**
- 최소 사용 코드(로그인 2종, DB 저장 1회, 파일 업로드 1회)를 esbuild로 압축 번들링해 gzip -9로 측정
- 버전: `@supabase/supabase-js` 2.118.0, `firebase` 13.1.0
- 현재 앱 첫 화면 JS는 gzip 376.6KB이고, NFR-05 허용치(+15%)는 약 56KB
- 두 SDK 모두 첫 화면에 넣으면 허용치를 넘으므로 지연 로딩이 필수다

## 결과

- 장점: 필수 조건 5개를 내장 기능으로 충족. 직접 작성하는 보안 코드 최소
- 단점·위험:
  - 무료 플랜 일시정지 정책(미확인)이 있으면 초기 저사용 기간에 백업이 멈출 수 있다. 다만 D-011 구조상 서버는 사본이라 앱 사용은 막히지 않고 백업이 "대기 중"이 된다(FR-CLOUD-09)
  - 공급자 종속. 완화책: 모든 서버 접근을 `storage.ts` 경계 뒤의 별도 모듈로 격리해 교체 범위를 제한
- 새로 생기는 비밀값: 서비스 역할 키(관리자 권한)는 클라이언트에 절대 넣지 않는다(NFR-03). 공개 키와 URL만 클라이언트 환경변수로 쓴다

| 항목 | 확인 방법 |

| 카카오 로그인 기본 지원, 카카오 쪽 요건(동의 항목, 사업자 인증 필요 여부) | Supabase 문서 "Login with Kakao", 카카오 개발자 문서 |
| 무료 플랜 일시정지 조건(기간), 무료 한도(DB, 파일, 월 사용자, 전송량) | Supabase 요금 페이지 |
