# ADR-002: 기기 간 백업 합치기와 기기 저장 구조 변경

- 상태: **Accepted** (결정 D-022, D-023). 세부 규칙 중 일부는 Proposed로 표시
- 날짜: 2026-10-30
- 관련 요구사항: FR-CLOUD-02, FR-CLOUD-04, FR-CLOUD-09, NFR-01

## 배경

같은 계정을 두 기기에서 쓰면, 사용자당 백업 묶음을 통째로 올리는 구조에서는 늦게 올린 기기가 다른 기기의 기록을 덮어써서 조용히 사라진다. 단순 합집합으로 합치면 한 기기에서 지운 기록이 되살아난다.

D-022로 "올리기 전 합치기 + 삭제 표시", D-023으로 "기록 단위 나중 수정 우선"을 정했다.

## 문제: 기기 간 같은 기록을 알아볼 방법이 없다

복원은 계정 간 덮어쓰기를 막기 위해 모든 기록에 **새 로컬 id**를 발급한다(CLAUDE.md). 따라서 같은 기록이라도 기기마다 id가 다르다. 날짜 단위인 `updatedAt`으로는 같은 날의 수정 순서도 알 수 없다.

## 결정

### 1. 기기 저장 구조에 필드 추가 (기존 원칙 "저장 구조 무변경"의 첫 예외)

| 대상 | 필드 | 내용 |
|---|---|---|
| 게임, 기록 | `syncId` | 생성 시 무작위 UUID. 기기를 옮겨도 변하지 않음. 로컬 키(`id`)와 별개 |
| 게임, 기록 | `updatedAtMs` | 마지막 수정 시각(밀리초) |
| 새 저장소 | 삭제 표시 `{ syncId, kind: 'game' \| 'play', deletedAtMs }` | 사용자별 |

- 로컬 키 규칙(복원 시 새 `id` 발급)은 바꾸지 않는다. `syncId`는 **같은 사용자 범위 안에서만** 비교하므로 계정 간 덮어쓰기 위험이 생기지 않는다.
- `syncId` 유지 규칙:
  - 백업 파일 복원과 클라우드 복원은 유지
  - 공유 링크로 받은 기록은 받는 사람의 새 기록이므로 **새로 발급**

### 2. 합치기 규칙 (순수 함수로 구현, 단위 테스트로 고정)

같은 사용자의 기기 데이터 L과 서버 백업 S를 합친다.

1. `syncId`가 같으면 같은 레코드다. `updatedAtMs`가 큰 쪽이 이긴다(D-023).
2. 한쪽에만 있는 레코드는 그대로 포함한다.
3. 삭제 표시가 있는 `syncId`는, 삭제 시각이 그 레코드의 `updatedAtMs`보다 나중이면 제외한다. 수정이 더 나중이면 되살린다(D-023 공통 규칙).
4. **(Proposed) 첫 합치기:** 클라우드 이전부터 있던 레코드는 기기마다 `syncId`가 따로 발급된다. `syncId`가 일치하지 않는 경우에만 기존 중복 판정 키로 같은 레코드인지 판단하고, 같으면 서버 쪽 `syncId`로 통일한다.
   - 게임: 게임 허브 키(FR-HUB-01)
   - 기록: 게임 키 + 날짜 + 시작 시각 + 참여자 이름 집합
5. 같은 `syncId`인데 양쪽 내용이 다르면 `backup_merge_conflict` 이벤트를 1회 보낸다(내용은 보내지 않음).

### 3. 올리기 절차 (낙관적 동시성)

1. 서버 백업과 버전 `v`를 받는다.
2. 기기 데이터와 합친다(규칙 2). 합친 결과를 기기에도 반영한다.
3. 버전이 여전히 `v`일 때만 저장하고 `v+1`로 올린다(조건부 업데이트).
4. 버전이 바뀌었으면 1로 돌아간다(최대 3회). 그래도 실패하면 상태를 "대기 중"으로 두고 나중에 재시도한다(FR-CLOUD-09).

### 4. 세부 수치

| 항목 | 값 | 상태 |
|---|---|---|
| 백업 묶음 대기 시간(FR-CLOUD-02) | 마지막 변경 후 5초 | Proposed |
| 삭제 표시 보관 기간 | 무기한(1건 약 60바이트 추정). 기한을 두면 오래 꺼져 있던 기기가 지운 기록을 되살릴 수 있음 | Proposed |
| 버전 충돌 재시도 | 최대 3회 | Proposed |

## 결과

- 장점:
  - 두 기기 모두 백업되고 삭제가 반영된다
  - 합치기는 순수 함수라 테스트로 고정할 수 있다
- 비용:
  - 기기 저장 구조 변경(필드 2개, 저장소 1개)과 기존 데이터 이전 작업(기존 레코드에 `syncId`, `updatedAtMs` 부여)
  - 백업 파일 형식에 `syncId`, `updatedAtMs`, 삭제 표시를 추가한다(이전 형식 파일도 계속 읽을 수 있어야 함)
- 위험:
  - 기기 시계 오차로 드물게 잘못된 쪽이 이길 수 있다(D-023, 이벤트로 관찰)
  - 첫 합치기의 내용 기반 판정(규칙 2-4)은 같은 날, 같은 시각, 같은 사람으로 같은 게임을 두 번 한 경우를 하나로 합칠 수 있다. 기존 백업 복원과 같은 한계다
